# dns-check

Squad beyond の配信ドメインの状態を、顧客自身が確認できる公開ツールです。

**このツールは設定を一切変更しません。** 公開されている情報を読み取って表示するだけなので、何度実行しても安全です。

タブが2つあります。

- **向き先の確認** — DNSレコードが正しく設定されているか
- **有効期限の確認** — ドメインが失効していないか、配信を止めるステータスが付いていないか

## 向き先の確認

ドメインを入力し、「サブドメインで配信」か「本ドメインで配信」を選んで実行します。ドメインを入力した時点でどちらかが自動選択されます。

| 配信方法 | 種別 | TTL | 内容 |
|---|---|---|---|
| サブドメイン（ホスト名は `sb` 推奨、任意） | CNAME | 3600 | `fallback.mysquadbeyond.com` |
| 本ドメイン | A | 3600 | `104.16.117.60` |

判定は 一致 / 不一致 / 未設定 の3つ。TTL は表示のみで判定には使いません（3600以外でも配信は動作するため）。

### DNS管理元の表示

**このツールを作った一番の理由がここです。**

ドメインを買った会社と、DNSレコードを実際に管理している場所は別々にできます。この2つがずれていると「設定したのに反映されない」が起きます。

例：お名前.comで取得したドメインのネームサーバーが AWS（Route 53）を向いている場合、お名前.comの「DNSレコード設定」画面でレコードを追加しても、参照されるのは Route 53 側なので何も起きません。制作会社がサイト構築時にネームサーバーを変更していて、顧客本人がそれを知らない、というケースで頻発します。

そこでゾーン頂点の NS レコードを引き、「どこで設定すべきか」を名指しで表示します。あわせて「ドメインを買った会社と管理場所が違うのはなぜ？」という説明を折りたたみで用意しています。

判定できる事業者：

- お名前.com（`*.dnsv.jp`）
- お名前.com レンタルサーバー（`*.gmoserver.jp`）
- Amazon Route 53（`*.awsdns-*`）
- Cloudflare / さくらインターネット / エックスサーバー / ロリポップ / heteml / ムームードメイン / バリュードメイン / ConoHa / Azure DNS / Wix

一覧にない事業者の場合は事業者名を出さず、NS の一覧と汎用の案内文を表示します。NS のドメイン名から顧客側で判断できることが多いためです。追加は `NS_PROVIDERS` に `[正規表現, 事業者名, 案内文]` を足してください。

### レコード一覧

CNAME / A / AAAA / TXT / MX / CAA を、値と TTL 付きで表示します。

## 有効期限の確認

判定は4段階です。

| 判定 | 条件 |
|---|---|
| 有効 | 期限まで31日以上 |
| 期限間近 | 30日以内 |
| 期限切れ | 期限を過ぎている |
| 停止中 | `client hold` / `pending delete` など、配信を止めるステータスが付いている |

**「停止中」が特に重要です。** DNS設定が正しくてもページが表示されないケースの原因になります。

表示内容は、有効期限（残日数付き）、登録日、最終更新日、登録会社、ステータス一覧。ステータスは `client transfer prohibited` のような英語コードに日本語の説明を付け、配信に影響するものだけ赤字にしています。

サブドメインを入力しても、大元のドメインを確認します（`sb.example.com` → `example.com`）。

### 確認できないドメイン

`.jp` `.de` `.eu` `.cn` `.kr` は非対応です。ICANN の RDAP 義務化は gTLD が対象で、これらの ccTLD は RDAP で情報を公開していません。該当する場合は「自動確認に対応していません」と専用のメッセージを表示します（エラー表示にはなりません）。

`.jp` を対応させるには `whois.jprs.jp` を叩く必要があり、サーバー（Cloudflare Worker など）が別途必要になります。

## 確認できないこと

- **SSL証明書の状態**（発行者・有効期限など）。ブラウザから証明書を直接確認する手段がないため。証明書エラーの調査には別途サーバー側の仕組みが必要です
- **DNSの伝播状況**。公開DNSにキャッシュされた応答を見ているため、設定直後は古い値が返ることがあります
- **社内ネットワーク固有の名前解決**。社内DNSで別の値を返している場合、このツールの結果と実際の見え方は一致しません

## 設定値の変更

`index.html` 内の `PRESET` を編集してください。

```js
var PRESET={
  sub:{type:'CNAME',value:'fallback.mysquadbeyond.com'},
  apex:{type:'A',value:'104.16.117.60'}
};
```

## 構成

- `index.html` — 単一ファイル。ビルド不要、依存パッケージなし、サーバー不要
- DNS照会は DNS over HTTPS。Cloudflare（`cloudflare-dns.com`）を優先し、失敗時に Google（`dns.google`）へフォールバック
- 登録情報の照会は RDAP。`.com` / `.net` は Verisign、`.org` は PIR のレジストリへ直接問い合わせ、それ以外と失敗時は `rdap.org` にフォールバック（`rdap.org` はリダイレクトを挟むぶん遅いため）
- すべての通信にタイムアウトを設定（DNS 8秒、RDAP 9秒）。応答がない場合は理由とともにエラーを表示します
- 問い合わせは閲覧者のブラウザから直接発行されるため、サーバーもログも不要
- NS はゾーンの頂点にしか存在しないため、`sb.example.co.jp` を入力しても `example.co.jp` に対して問い合わせます。`co.jp` のような2階層TLDにも対応

## デプロイ

静的ホスティングにファイルを置くだけです。Cloudflare Pages / GitHub Pages とも、ルートに `index.html` があれば動きます（ビルドコマンドは不要）。

公開URLは https://squadbeyond-domain-check.pages.dev です。
旧URL（https://squad-customersupport.github.io/domain-check/）は、新URLへの案内ページに変わっています。すでに案内した人がたどり着けるように残してあるだけです。

### 直しかた

1. GitHubで **`main` ブランチの** `index.html` を開き、鉛筆アイコンから編集する
2. Commit changes を押す
3. 1〜2分で公開URLに反映される

コマンドを打つ必要はありません。`main` を更新すると GitHub Actions が動き、Cloudflare Pages へ自動でアップロードされます（`.github/workflows/deploy.yml`）。反映されないときは GitHubの **Actions** タブにエラーが出ています。手動でやり直す場合は Actions タブ →「Deploy to Cloudflare Pages」→「Run workflow」。

ブランチは2つあります。`main` がツール本体で、直すのはこちら。`gh-pages` は旧URLの案内ページ専用なので触る必要はありません。

顧客が「これは公式のツールか」と迷わないよう、`squadbeyond.com` 配下のサブドメインか、FAQサイト配下に置くことを推奨します。Cloudflare Pages のカスタムドメインを当てれば、末尾が `pages.dev` のURLを顧客に見せずに済みます。ただし `squadbeyond.com` のDNSは Route 53（AWS）で管理されているため、CNAMEの追加はAWS側の作業になります。

## 動作確認

`index.html` をブラウザで直接開けば動きます（`file://` でも DoH / RDAP は動作します）。
